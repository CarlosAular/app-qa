Cocos · App bajo prueba

Puesta en marcha

Cómo levantar la app a mano en un simulador de iOS y en un emulador de Android, desde una Mac sin nada instalado. 1 · Qué necesitás antes de empezar

Esta app no corre en el navegador: es una app nativa. Para iOS necesitás una Mac con Xcode. Para Android alcanza con el SDK por línea de comandos y un JDK — no hace falta instalar Android Studio. Las versiones de la derecha son con las que se verificó que funciona.

Si Bun no está instalado, alcanza con:

npm install -g bun
Cuánto tarda la primera vez

Para iOS, contando la descarga del runtime (8,5 GB), la instalación de dependencias y el build en frío, calculá entre 30 y 45 minutos. Para Android, entre el SDK (5,8 GB) y el primer build de Gradle, otro tanto. Las veces siguientes, con todo cacheado, la app levanta en menos de un minuto.

2 · Levantar la app, paso a paso

Los dos primeros pasos son iguales para todos. Después seguí la vía de la plataforma que quieras levantar — o las dos, que conviven sin pisarse.

Pasos comunes

  1. Instalar las dependencias

    Descarga los 919 paquetes de JavaScript del proyecto. Tarda unos 15 segundos. 

    bun install

  2. Crear el archivo de configuración

    Copiá el ejemplo y completá EXPO_PUBLIC_CANDIDATE_ID con un valor propio (por ejemplo tu nombre). Sin ese valor la app no arranca. 

    cp .env.example .env

Vía iOS

  1. Generar el proyecto nativo

    Crea la carpeta ios/ con el proyecto de Xcode. Es un paso generado: la carpeta no está en el repositorio. Sin el --platform genera las dos. 

    bunx expo prebuild --platform ios

  2. Asegurarte de tener un simulador

    Si este comando no lista ningún iPhone, no tenés ningún runtime instalado — ver el obstáculo A más abajo. 

    xcrun simctl list devices available

  3. Compilar y lanzar

    Compila la app, la instala en el simulador, la abre y levanta Metro. El LANG es obligatorio — ver el obstáculo B. 

    export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8
bun run ios
Metro se cae al terminar el build

Si macOS no le dio permiso de automatización a la terminal, bun run ios falla al final intentando traer la ventana del simulador al frente, y se lleva puesto a Metro. La app ya quedó instalada, así que alcanza con levantar Metro por separado y relanzarla: 

bun run start
xcrun simctl launch booted com.cocos.trading

Vía Android

Esta vía no usa Android Studio. Todo se hace por terminal con el SDK de línea de comandos, que es además lo único que pide Appium para la suite E2E automatizada (ver README, sección "Suite E2E automatizada (Appium)").

  1. Instalar el JDK 17 y el SDK

    Gradle necesita Java 17 para compilar. Ojo con el java que ya trae macOS: ver el obstáculo C. 

    brew install openjdk@17
brew install --cask android-commandlinetools

  2. Dejar las variables en el shell

    Agregá esto al final de tu ~/.zshrc y abrí una terminal nueva. Sin ANDROID_HOME las herramientas no encuentran el SDK. 

    export JAVA_HOME="/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export ANDROID_SDK_ROOT="$ANDROID_HOME"
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"

  3. Aceptar las licencias e instalar los componentes

    Son unos 5,8 GB entre el SDK, el emulador y la imagen del sistema. La imagen tiene que ser arm64-v8a si tu Mac es Apple Silicon — ver el obstáculo E. 

    yes | sdkmanager --sdk_root="$ANDROID_HOME" --licenses

sdkmanager --sdk_root="$ANDROID_HOME" \
  "platform-tools" "platforms;android-36" "build-tools;36.0.0" \
  "emulator" "cmdline-tools;latest" \
  "system-images;android-36;google_apis;arm64-v8a"

  4. Crear el emulador y levantarlo

    Un Pixel 8 con Android 16. El emulador queda ocupando la terminal, así que mandalo al fondo con & o usá otra pestaña. 

    avdmanager create avd -n Pixel_8_API_36 \
  -k "system-images;android-36;google_apis;arm64-v8a" -d pixel_8

emulator -avd Pixel_8_API_36 &
adb devices   # tiene que listarlo como "device"

  5. Generar el proyecto nativo y compilar

    El primer build de Gradle descarga medio internet y tarda bastante; los siguientes son de segundos. 

    bunx expo prebuild --platform android
bun run android

3 · Obstáculos conocidos

Ninguno está documentado en el README del proyecto y todos frenan el primer intento en una máquina limpia. Los dos primeros son de iOS; los otros cuatro aparecieron al montar Android desde cero. Todos están verificados en esta Mac, no copiados de un foro.

Obstáculo A — Xcode instalado pero sin ningún simulador

Xcode se puede instalar sin runtimes de iOS. Cuando pasa, xcrun simctl list devices available no lista ningún dispositivo y el build falla sin un mensaje claro. 

# Descarga el runtime (~8,5 GB, 15-25 min)
xcodebuild -downloadPlatform iOS

# Comprobar que quedó
xcrun simctl list runtimes | grep iOS

Al instalarse el runtime aparecen solos los dispositivos por defecto. Booteá uno antes de compilar: 

xcrun simctl boot "iPhone 17 Pro"

Obstáculo B — CocoaPods rompe por el idioma del sistema

Si tu terminal no está en UTF-8, pod install muere con un error que no dice nada sobre el idioma: 

Unicode Normalization not appropriate for ASCII-8BIT
(Encoding::CompatibilityError)

La solución es exportar el locale antes de compilar:

export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8

Para no repetirlo en cada sesión, agregalo a tu ~/.zshrc. El propio CocoaPods lo avisa en un warning que es fácil pasar por alto.

Obstáculo C — el java que ya tenés no sirve

Es el más engañoso de todos, porque java -version responde perfecto y te hace creer que estás listo. macOS suele traer un JRE 1.8 del viejo plugin de applets: 

java version "1.8.0_461"
Java(TM) SE Runtime Environment (build 1.8.0_461-b11)

Eso no compila nada: es un runtime para correr Java, no un kit para desarrollar, y además Gradle 9 pide Java 17 como mínimo. La pista de que estás en este caso es que /usr/libexec/java_home -V sólo lista una entrada y dice JavaAppletPlugin. Instalá un JDK de verdad y apuntá JAVA_HOME ahí: 

brew install openjdk@17
export JAVA_HOME="/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"

java -version   # ahora tiene que decir 17.x
Por qué openjdk y no Zulu

Los docs de Expo recomiendan brew install --cask zulu@17. Funciona igual, pero es un .pkg que instala en /Library y te pide la contraseña de administrador. La fórmula openjdk@17 instala dentro de Homebrew sin pedir sudo, y a Gradle le da exactamente lo mismo: las dos son OpenJDK 17.

Obstáculo D — avdmanager no encuentra el SDK

Al intentar crear el emulador, esto: un error que nombra la lista de imágenes válidas y acto seguido dice que la lista es null. 

Error: Package path is not valid. Valid system image paths are:
null

No es que falte la imagen — está instalada y sdkmanager --list_installed la muestra. El problema es que el avdmanager que Homebrew deja en /opt/homebrew/bin busca el SDK al lado suyo, y tu SDK está en otro lado. Exportar ANDROID_SDK_ROOT no alcanza. La solución es instalar las cmdline-tools adentro del SDK y usar ese binario, que además es el layout que esperan Expo y Appium: 

sdkmanager --sdk_root="$ANDROID_HOME" "cmdline-tools;latest"

# y poné este bin en el PATH, antes que el de Homebrew
export PATH="$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"

Obstáculo E — la imagen del emulador tiene que ser arm64

En una Mac con chip M (Apple Silicon) la imagen del sistema tiene que ser arm64-v8a. Si agarrás una x86_64 el emulador no bootea, o bootea tan lento que parece colgado, porque está emulando otra arquitectura. 

# Correcta en Apple Silicon
system-images;android-36;google_apis;arm64-v8a

# Verificar qué arquitectura tenés
uname -m   # arm64 = Apple Silicon

Obstáculo F — --device con el ID de adb no funciona

Parece lógico pasarle a Expo el identificador que devuelve adb devices, pero no lo reconoce: 

CommandError: Could not find device with name: emulator-5554

Expo espera el nombre del AVD, no el serial de adb. Si tenés un solo emulador prendido, lo más simple es no pasarle nada y dejar que lo elija solo: 

bun run android

4 · Variables de entorno

El archivo .env maneja todas las llamadas a la API. Se leen al compilar el bundle, no al arrancar: si cambiás una, tenés que reiniciar Metro para que tome efecto.

Variable Obligatoria Qué hace
EXPO_PUBLIC_API_URL sí Dirección de la API. Valor: https://dummy-api-topaz.vercel.app
EXPO_PUBLIC_CANDIDATE_ID sí Tu cuenta. Aísla órdenes, efectivo y tenencias del resto. Cualquier texto no vacío. La app lanza un error y no arranca si falta.
EXPO_PUBLIC_BUGS_TIER no Nivel de defectos inyectados en la API: off, easy, medium o hard. Cualquier otro valor cae a off. Para uso normal, dejalo en off. Hay un script por nivel: bun run start:easy, ios:hard, android:medium y test:api:easy.
Opcional: token de Qase para publicar corridas

Sólo hace falta si vas a publicar resultados en Qase; para levantar la app y correr las suites en local no se necesita. Generalo en app.qase.io/user/api/token y guardalo en el .env (está ignorado por git): QASE_TESTOPS_API_TOKEN=<token>. Después, los scripts bun run publish:api (y publish:api:easy, :medium, :hard, :defectos) publican la corrida de la API en el proyecto COCOS; los test:api* corren sólo en local. Es un secreto: no lo compartas ni lo subas al repositorio.

8 · Levantar los dispositivos a mano

Esta sección es para el día después: ya está todo instalado y te querés sentar a ejecutar casos. Acá no se compila nada, sólo se prende lo que ya existe. Si arrancás de cero, andá primero a la sección 2.

Tres formas de levantarla

No hay una sola, y elegir mal te hace esperar de más. La diferencia entre ellas es cuánto trabajo hacen: desde sólo abrir lo que ya existe, hasta recompilar la app entera.

Forma Para qué sirve Cuándo usarla
A · Metro y una tecla Levantás Metro y apretás una letra. Él se encarga de prender el dispositivo y abrir la app El día a día. Es la más corta y la que menos hay que recordar
B · Comandos sueltos Vos controlás cada paso: qué dispositivo, cuándo abrir la app, cuándo cerrarla Cuando tenés varios dispositivos y querés uno puntual, o cuando armás un script. Son además los comandos que vas a usar para capturas, logs y reset
C · Compilar y correr Compila, instala y abre, además de levantar Metro La primera vez, o después de tocar dependencias nativas, app.config.ts o plugins de Expo
Si tenés dudas, empezá por la A

Las tres terminan en lo mismo: la app abierta y conectada a Metro. La C es la única que recompila, y por eso es la más lenta — no la uses por costumbre.

Forma A · Metro y una tecla

Metro no es sólo un servidor: mientras corre, te escucha el teclado. Todo pasa en una sola terminal.

  1. Levantar Metro

    Se queda corriendo. No cierres esta pestaña mientras testeás.

    bun run start

  2. Apretar la letra de tu plataforma

    Sobre esa misma terminal, sin escribir nada más. i prende el simulador de iOS y abre la app; a hace lo mismo con el emulador de Android. Si el dispositivo no estaba prendido, lo prende él. 

    i   # iOS
a   # Android

Las demás teclas que ofrece, útiles mientras testeás:

Tecla Qué hace
r Recarga la app sin recompilar
m Abre el menú de desarrollo dentro de la app — lo mismo que Cmd+D en iOS
j Abre React Native DevTools, con la pestaña Network donde ves cada request
? Lista todas las teclas
La limitación de esta forma

Con i no elegís qué simulador. Agarra el que esté prendido, o el que el sistema considere por defecto. Si tenés varios y la app está instalada sólo en uno —que es el caso de esta Mac, donde vive en el iPhone 17 Pro— puede abrirte el equivocado. Para eso está la forma B.

Forma B · Comandos sueltos

Más tecleo, pero controlás exactamente qué dispositivo y en qué momento. Es también la forma que vas a scriptear.

  1. Levantar Metro, en su propia pestaña

    Igual que en la forma A: se queda corriendo y ocupa la terminal, así que va aparte. 

    bun run start

  2. Prender el dispositivo que querés

    En iOS nombrás el simulador; en Android, el AVD. El de Android tarda cerca de 20 segundos en estar listo, así que conviene esperarlo antes de seguir. 

    # iOS
xcrun simctl boot "iPhone 17 Pro"
open -a Simulator

# Android
emulator -avd Pixel_8_API_36 &
adb wait-for-device
until [ "$(adb shell getprop sys.boot_completed 2>/dev/null | tr -d '\r')" = "1" ]; do sleep 2; done

  3. Abrir la app

    Ya está instalada del build anterior. Este es el único comando que vas a repetir durante el día. 

    # iOS
xcrun simctl launch booted com.cocos.trading

# Android
adb shell am start -n com.cocos.trading/.MainActivity
Por qué el until en Android y no un loop adentro de adb shell

Parece lo mismo pero no lo es. adb wait-for-device vuelve apenas adb ve el dispositivo, que es mucho antes de que Android termine de arrancar. Si la espera corre adentro de adb shell y esa conexión falla en esos primeros segundos, el comando sale al toque, el loop nunca espera y el am start se dispara contra un sistema que todavía no está listo: el emulador queda abierto y la app no aparece, sin ningún error visible. Corriendo el until del lado de la Mac, cada intento fallido se reintenta.

En iOS no hace falta esperar nada: simctl launch aguanta solo si el simulador todavía está arrancando.

Forma C · Compilar y correr

Un solo comando que hace todo: compila, instala en el dispositivo, abre la app y levanta Metro. Es la de la sección 2, la que usaste la primera vez. 

export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8   # sólo iOS, ver obstáculo B
bun run ios

# o
bun run android

La contra es que pasa por el compilador igual aunque no hayas tocado nada. Si sólo cambiaste código de pantallas, no te hace falta: eso lo recarga Metro solo. Reservala para cuando cambió algo nativo:

  • Instalaste o sacaste una dependencia con parte nativa.
  • Tocaste app.config.ts — nombre, ícono, permisos, scheme, plugins.
  • Borraste las carpetas ios/ o android/.

Qué se repite y qué no

La secuencia completa es para empezar la sesión. Después casi nada se repite: Metro y el dispositivo se quedan prendidos hasta que los apagues o reinicies la Mac. Lo único que vas a volver a usar durante el día es el launch.

Comando Cada cuánto Si lo repetís igual
bun run start Una vez por sesión Falla: el puerto 8081 ya está ocupado por el Metro que tenés andando
simctl boot · emulator -avd Una vez por sesión Da error "Unable to boot device in current state: Booted". Molesto pero inofensivo: el simulador sigue como estaba
open -a Simulator Sólo si cerraste la ventana Nada, la trae al frente
simctl launch · am start Cada vez que abrís la app Si ya está abierta no la reinicia: te devuelve el mismo proceso — ver el aviso de abajo
Para reiniciar la app de verdad hay que cerrarla primero

Es una trampa fácil cuando encadenás casos de prueba: corrés launch creyendo que arrancás de cero, y en realidad te quedaste en la app que ya estaba abierta, con su estado y su navegación intactos. Se nota en el número de proceso: si launch te devuelve el mismo de antes, no reinició nada. 

# iOS
xcrun simctl terminate booted com.cocos.trading
xcrun simctl launch booted com.cocos.trading

# Android
adb shell am force-stop com.cocos.trading
adb shell am start -n com.cocos.trading/.MainActivity

Qué tiene que estar prendido

Son tres piezas, y cuando algo "no abre" casi siempre es que falta una. Entender qué hace cada una te ahorra la mitad de los problemas.

Pieza Qué es Cómo comprobás que está
El dispositivo El simulador de iPhone o el emulador de Android: una computadora virtual corriendo dentro de tu Mac xcrun simctl list devices booted · adb devices
Metro El servidor que le pasa el JavaScript a la app. Lo que instalaste en el dispositivo es sólo el cascarón nativo: el código de las pantallas se lo pide a Metro cada vez que arranca curl -s localhost:8081/status tiene que responder packager-status:running
La app instalada El APK o el .app ya compilado, adentro del dispositivo. Sobrevive a que lo apagues: no hace falta recompilar cada vez adb shell pm list packages | grep cocos

Si algo no arranca

Buscá lo que ves en pantalla en la primera columna. Están ordenados por frecuencia: los primeros tres son el 90% de los casos.

Lo que ves Qué está pasando Cómo se arregla
Pantalla negra que no se va Metro no está levantado, o la app no lo encuentra. Unos segundos de negro al abrir son normales — está bajando el bundle bun run start en otra pestaña
Unable to lookup app Booteaste un simulador donde la app no está instalada. Cada simulador tiene su propio disco, y la app quedó sólo en el que usaste para compilar Booteá el iPhone 17 Pro
Cambiaste el .env y la app lo ignora Las EXPO_PUBLIC_* quedan escritas adentro del bundle cuando Metro lo arma. No se leen en vivo, y la app no avisa nada Cortá Metro y arrancalo con bunx expo start --clear
adb devices no lista nada El emulador todavía está booteando adb wait-for-device
command not found: adb o emulator Las variables del SDK no están cargadas en esa terminal Abrí una terminal nueva, o source ~/.zshrc
El simulador queda en el logo de Apple Todavía está booteando. boot devuelve enseguida, pero el arranque sigue por detrás xcrun simctl bootstatus "iPhone 17 Pro" -b espera a que termine

Ver en qué simuladores está instalada la app

Responde sin necesidad de bootear ninguno. Si no aparece ninguno, la app no está compilada todavía: volvé a la sección 2. 

for u in $(xcrun simctl list devices available | grep -oE '[0-9A-F-]{36}'); do
  if find ~/Library/Developer/CoreSimulator/Devices/"$u"/data/Containers/Bundle/Application \
       -maxdepth 2 -name "Cocos.app" 2>/dev/null | grep -q .; then
    xcrun simctl list devices | grep "$u"
  fi
done

Durante la sesión de testing

Recargar la app sin recompilar

Si tocaste código de pantallas, Metro la recarga sola. Para forzarlo, lo más corto es apretar r en la terminal de Metro. Si querés el menú de desarrollo completo, es m desde ahí, Cmd+D en el simulador de iOS, o este comando en Android: 

adb shell input keyevent 82

Ver los logs mientras testeás

Lo primero que hay que saber es lo que nadie te dice: esta app casi no loguea. En todo el código hay un solo console, y está en el catch del interceptor de red — o sea que sólo escribe algo cuando un request falla. Si navegás y todo anda bien, la terminal te va a quedar vacía. No es que el filtro esté mal: no hay nada para mostrar.

Esto es lo que da cada vía, medido en esta máquina y no copiado de la documentación oficial:

Vía Qué ves Sirve
adb logcat -s ReactNativeJS:V Nada. Cero líneas. Ese tag no existe en React Native 0.85 con la arquitectura nueva, aunque es lo que vas a encontrar en cualquier tutorial no
adb logcat --pid=$(adb shell pidof com.cocos.trading) Tres líneas de hiddenapi de la capa de accesibilidad. Nada de la app no
xcrun simctl spawn booted log stream sin filtrar 878 líneas por cada arranque, casi todo de com.apple.network y UIKit no
El mismo, filtrado a las URLs La URL de cada request, en vivo. Headers y cuerpo no aparecen sí, iOS
React Native DevTools Pestaña Network con cada request, sus headers y su respuesta completa sí, las dos

Para seguir los endpoints desde la terminal (iOS). Deja corriendo una línea por cada llamada a la API a medida que navegás. Es lo más cerca que vas a estar de "ver los logs en vivo" sin salir de la consola: 

xcrun simctl spawn booted log stream --predicate 'process == "Cocos"' --style compact \
  | grep --line-buffered -oE 'url: https://dummy-api-topaz[^ ,]+'

Para ver headers y respuestas (las dos plataformas). Abrí el menú de desarrollo y elegí Open DevTools. La pestaña Network te muestra cada request entero, que es donde vas a poder comprobar cosas como que x-platform cambia entre iOS y Android, o qué manda exactamente la app al crear una orden.

Lo más rápido es la tecla j sobre la terminal de Metro: abre DevTools directo, sin pasar por el menú, y sirve para las dos plataformas. Si preferís ir por el menú de la app: 

# Desde la terminal de Metro, para cualquiera de las dos
j

# O abriendo el menú de desarrollo dentro de la app:
#   Metro: la tecla m
#   iOS:   Cmd+D en la ventana del simulador
#   Android:
adb shell input keyevent 82
Comprobar que el depurador está enganchado

Si Open DevTools no abre nada, primero fijate que Metro vea el dispositivo. Esto lista un target por cada app conectada: 

curl -s http://localhost:8081/json/list | jq -r '.[].deviceName'

Volver la cuenta a cero entre casos

Acá hay un detalle propio de esta app: el saldo, las órdenes y la tenencia no viven en el teléfono, viven en la API, separados por EXPO_PUBLIC_CANDIDATE_ID. Borrar los datos locales te deja la cuenta exactamente como estaba. 

# Caché de pantallas (Android)
adb shell pm clear com.cocos.trading

# Saldo, órdenes y tenencia: eso se borra contra la API
curl -s -X POST "https://dummy-api-topaz.vercel.app/reset" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular"

Para empezar como un usuario nuevo, sin borrarle nada al anterior, cambiá EXPO_PUBLIC_CANDIDATE_ID en el .env y reiniciá Metro con --clear. La API te trata como otro inquilino, con su millón de pesos intacto. Todo el detalle está en el documento de la API.

Al terminar

El emulador de Android consume bastante CPU y batería aunque esté quieto, así que conviene apagarlo. Metro se corta con Ctrl+C en su pestaña. 

adb emu kill                    # apaga el emulador de Android
xcrun simctl shutdown booted    # apaga el simulador de iOS
