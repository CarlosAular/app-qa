1 · Headers obligatorios

Toda request necesita estos dos headers. Sin ellos la API responde 400.

X-Enable-Bugs — en todos los endpoints

Nivel de defectos inyectados: off, easy, medium o hard. No distingue mayúsculas (OFF funciona). Ausente o con cualquier otro valor: 

{"error": "X-Enable-Bugs must be off, easy, medium, or hard"}

off es el camino sano y la línea base contra la que se escriben las verificaciones.

X-Candidate-Id — en portfolio, orders y reset

Identifica la cuenta. Ausente o vacío:

{"error": "Missing X-Candidate-Id header"}
  • Distingue mayúsculas: carlos y CARLOS son dos cuentas distintas (observado).
  • /instruments y /search no lo requieren: los instrumentos son compartidos.
  • No hay autenticación: cualquiera que conozca un id puede leer y modificar esa cuenta.

Headers que la app agrega y la API ignora

X-Device-IP, X-App-Bundle-ID, X-Platform, X-Device-Model, X-Device-Manufacturer, X-Device-Name, X-Device-OS-Version, X-App-Version, X-Device-ID.

2 · Endpoints

Seis endpoints, más un health check que la app no consume.

Los bloques "copiar y pegar" andan tal cual

Cada endpoint termina con un bloque listo para pegar en la terminal: URL completa, headers y todo. No hace falta correr nada antes. Sólo dos cosas:

  • Los ejemplos usan carlos-aular como X-Candidate-Id, que es el valor del .env de este proyecto. Cambialo si querés operar sobre otra cuenta — cualquier string sirve y crea un inquilino nuevo con su millón de pesos.
  • Van con | jq para que la respuesta se lea. Si no tenés jq, instalalo con brew install jq o borrá ese pedazo.

Los POST escriben de verdad sobre la cuenta del candidate-id que pongas. El de /reset borra todo sin preguntar.

GET /instruments sin candidate-id

Listado completo de instrumentos. Compartido y de sólo lectura.

Campo Tipo Notas
id number Entero, 1 a 26
ticker string Ej. DYCA
name string Ej. Dycasa S.A.
type string ACCIONES o MONEDA
last_price number ARS, hasta 2 decimales
close_price number ARS, cierre previo 
[
  {"id": 1, "ticker": "DYCA", "name": "Dycasa S.A.",
   "type": "ACCIONES", "last_price": 45.72, "close_price": 50.07},
  {"id": 26, "ticker": "ARS", "name": "Pesos",
   "type": "MONEDA", "last_price": 1, "close_price": 1}
]

Observado: 26 instrumentos, 25 acciones y una moneda. Los precios son estables entre requests — no hay simulación de mercado en vivo, lo que hace determinísticas las aserciones sobre precio. El retorno diario no viene en la respuesta: lo calcula el cliente.

Copiar y pegar

curl -s "https://dummy-api-topaz.vercel.app/instruments" \
  -H "X-Enable-Bugs: off" | jq

# Sólo ticker y precio de cada instrumento
curl -s "https://dummy-api-topaz.vercel.app/instruments" \
  -H "X-Enable-Bugs: off" | jq -r '.[] | "\(.ticker)\t\(.last_price)"'
GET /search?query= sin candidate-id

Búsqueda de instrumentos. Devuelve el mismo esquema que /instruments.

Entrada Resultado
DYCA 1 resultado
dyca 1 resultado — no distingue mayúsculas
DY (prefijo) 1 resultado
YCA (sufijo) 1 resultado — matchea substring, no sólo prefijo
Dycasa, Telecom 0 resultados — sólo matchea ticker
" DYCA " 0 resultados — no recorta espacios
sin parámetro 26 resultados — devuelve todo el catálogo
ZZZZ, *, %, inyección SQL, XSS 0 resultados, sin error

No hay paginación ni límite de resultados.

Copiar y pegar

curl -s "https://dummy-api-topaz.vercel.app/search?query=DYCA" \
  -H "X-Enable-Bugs: off" | jq

# Los casos borde de la tabla de arriba, uno por línea
# (el último no lleva query: devuelve el catálogo entero)
for q in DYCA dyca DY YCA Dycasa ZZZZ ""; do
  printf "%-8s -> " "$q"
  curl -s "https://dummy-api-topaz.vercel.app/search?query=$q" \
    -H "X-Enable-Bugs: off" | jq 'length'
done
GET /portfolio requiere candidate-id

Estado de la cuenta. Cuenta nueva: {"cash": 1000000, "holdings": []}. 

{
  "cash": 999542.8,
  "holdings": [
    {"instrument_id": 1, "ticker": "DYCA", "quantity": 10,
     "last_price": 45.72, "close_price": 50.07,
     "avg_cost_price": 45.72}
  ]
}

cash y quantity vienen netos de las reservas de las órdenes pendientes.

La aserción de más valor de toda la suite

No hay saldo almacenado: efectivo y tenencias se derivan de las órdenes ejecutadas. Verificar esa derivación contra el historial es lo que más cubre por unidad de esfuerzo.

Copiar y pegar

curl -s "https://dummy-api-topaz.vercel.app/portfolio" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq

# Sólo el efectivo, para comparar contra el cálculo esperado
curl -s "https://dummy-api-topaz.vercel.app/portfolio" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq '.cash'

Leer el historial es lo que dispara la resolución de las órdenes límite pendientes.

Copiar y pegar

curl -s "https://dummy-api-topaz.vercel.app/orders" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq

# Cuántas hay de cada estado — ojo que este GET resuelve las pendientes
curl -s "https://dummy-api-topaz.vercel.app/orders" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq 'group_by(.status) | map({estado: .[0].status, n: length})'

Envío de una orden. Responde 201 con la orden creada.

Campo Obligatorio Reglas

POST /reset requiere candidate-id

Borra órdenes, efectivo y tenencias. Responde {"ok": true}. Tras el reset: cash = 1000000, sin tenencias, historial vacío. No pide confirmación ni es reversible.

Copiar y pegar

# Borra TODO el estado de este candidate id. No pide confirmación.

  -H "X-Enable-Bugs: off" \

3 · Reglas de negocio

Ejecución y ciclo de las reservas de saldo.

Tipo Al crearse Precio de ejecución
MARKET FILLED inmediato Último precio del instrumento
LIMIT Siempre PENDING Se resuelve después

Ciclo de la reserva

Toda orden aparta saldo en el momento de crearse.

Estado Efecto sobre la reserva Efecto en el portafolio
PENDING La mantiene Efectivo o cantidad reducidos
FILLED La liquida Se materializa el movimiento
REJECTED La libera Vuelve el saldo
  • Una compra reserva cantidad × precio de efectivo.
  • Una venta reserva cantidad acciones.

Observado: con $ 999.542,80 y 10 DYCA, una venta límite de 5 DYCA deja el efectivo intacto y baja la tenencia a 5; una compra límite de 10 CAPX a $ 40 baja el efectivo en exactamente $ 400 sin crear ninguna tenencia.

4 · Resolución de órdenes límite

No determinística y perezosa. Es el comportamiento más importante a la hora de diseñar tests estables.

La resolución se dispara al leer el estado de la cuenta, no por el paso del tiempo (observado). Creada una orden límite, el primer o segundo read ya la deja resuelta, y a partir de ahí el estado es terminal. 

create           -> PENDING
GET /orders  #1  -> PENDING
GET /orders  #2  -> REJECTED   (terminal, no cambia más)
Leer el portafolio también la resuelve

Tras crear una compra límite y leer únicamente /portfolio seis veces, la orden ya estaba resuelta antes del primer GET /orders: en una corrida ejecutada con la tenencia creada, en dos rechazada con el efectivo devuelto.

Observado: una compra límite ejecutable de 1 DYCA a $ 60 reserva $ 60 al crearse pero ejecuta al último precio ($ 45,72) y libera el excedente — el efectivo final fue $ 999.954,28.

Distribución medida

60 órdenes límite sobre DYCA con último precio $ 45,72, defectos en off. Se llama ejecutable a una compra con precio ≥ último, o a una venta con precio ≤ último.

Caso Ejecutadas Pendientes Rechazadas
Compra ejecutable (precio ≥ último) 4 0 11
Compra no ejecutable (precio < último) 0 2 13
Venta ejecutable (precio ≤ último) 6 0 9
Venta no ejecutable (precio > último) 0 2 13
Invariante utilizable en tests

Una orden límite no ejecutable nunca se ejecuta: 0 de 30 observadas. Una ejecutable puede terminar en cualquiera de los tres estados.

Consecuencias para la automatización

  • Nunca asertar un estado final concreto de una orden límite: asertar pertenencia a un conjunto — los tres estados para las ejecutables, sólo pendiente o rechazada para las que no lo son.
  • Cuando se necesita una ejecución determinística, usar una orden a mercado.
  • No existe forma confiable de observar una orden pendiente "en reposo": cualquier lectura de la cuenta puede resolverla. La reserva se verifica con la respuesta del propio POST y con una única lectura posterior, asertando de forma condicional según el estado que traiga.
  • Asertar invariantes —conservación de efectivo, liberación de reservas— en vez de estados puntuales.

5 · Aislamiento y persistencia

Cómo hacer que dos corridas de tests no se pisen.

  • El estado persiste entre corridas. Dos ejecuciones con el mismo candidate-id interfieren entre sí.
  • El id es arbitrario: se pueden generar ids únicos por corrida o por caso para paralelizar sin depender del reset.
Entornos donde el reset no existe

La estrategia pasa a asertar deltas en vez de valores absolutos: leer el estado, ejecutar la acción, asertar la diferencia esperada (efectivo_después = efectivo_antes − cantidad × precio). Los ids únicos por corrida son el complemento natural.

Cómo autoverificar la suite

Una suite bien construida debería fallar al menos en: control de tenencia (desde easy), código de estado de creación (desde medium) y precio de ejecución (en hard). Si al subir el nivel la suite sigue toda en verde, es que no está asertando comportamiento real.

7 · Anomalías observadas

Desviaciones respecto de lo documentado o de lo esperable, todas con los defectos en off — es decir, no son los defectos inyectados.

# Anomalía Evidencia
A1 La cantidad se coacciona en vez de validarse por tipo. Un cliente con un bug de serialización puede enviar 1000 acciones creyendo enviar un texto "10"⇒10 · "1e3"⇒1000 · " 7 "⇒7 · true⇒1 · [5]⇒5, todas ejecutadas. Sólo "10abc" y null dan 400
A9 Los GET mutan estado. Observar la cuenta altera el resultado y vuelve inobservable una orden pendiente estable Tanto /orders como /portfolio resuelven las límite
A2 Una orden límite con precio cero o negativo es aceptada price: -10 ⇒ 201 pendiente
A6 Se puede comprar ARS (la moneda) como si fuera una acción instrument_id: 26 ⇒ 201 ejecutada a $ 1
A3 La búsqueda sin parámetro devuelve todo el catálogo GET /search ⇒ 26 items

8 · Recetas de verificación

Para explorar a mano desde la terminal.

API=https://dummy-api-topaz.vercel.app
CID=tu-candidate-id
H=(-H "X-Enable-Bugs: off" -H "X-Candidate-Id: $CID")

# Estado limpio
curl -s -X POST "$API/reset" "${H[@]}"

# Catálogo y búsqueda
curl -s "$API/instruments" -H "X-Enable-Bugs: off"
curl -s "$API/search?query=DYCA" -H "X-Enable-Bugs: off"

# Portafolio inicial -> {"cash":1000000,"holdings":[]}
curl -s "$API/portfolio" "${H[@]}"

# Compra a mercado
curl -s -X POST "$API/orders" "${H[@]}" \
  -H "Content-Type: application/json" \
  -d '{"instrument_id":1,"side":"BUY","type":"MARKET","quantity":10}'

# Verificar la derivación: 1000000 - 10*45.72 = 999542.80
curl -s "$API/portfolio" "${H[@]}"

# Orden límite: siempre nace pendiente
curl -s -X POST "$API/orders" "${H[@]}" \
  -H "Content-Type: application/json" \
  -d '{"instrument_id":1,"side":"SELL","type":"LIMIT","quantity":5,"price":84.5}'

Reset completo antes de un caso

"Resetear la app" son en realidad dos cosas distintas, y confundirlas hace perder tiempo. El saldo, las órdenes y la tenencia no viven en el teléfono: viven en la API, separados por X-Candidate-Id. Borrar los datos locales deja la cuenta exactamente como estaba.

Qué querés borrar Dónde vive Con qué
Saldo, órdenes, tenencias La API, por candidate id POST /reset
Caché de pantallas, estado de navegación El dispositivo pm clear · reinstalar
Empezar como un usuario nuevo Ninguno de los dos Cambiar el candidate id en .env

Copiar y pegar

# 1 · Cuenta a cero en la API
curl -s -X POST "https://dummy-api-topaz.vercel.app/reset" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq

# 2 · Comprobar: cash 1000000, holdings vacío, sin órdenes
curl -s "https://dummy-api-topaz.vercel.app/portfolio" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq
curl -s "https://dummy-api-topaz.vercel.app/orders" \
  -H "X-Enable-Bugs: off" \
  -H "X-Candidate-Id: carlos-aular" | jq 'length'

# 3 · Estado local del dispositivo (Android)
adb shell pm clear com.cocos.trading

# 3 · Estado local del dispositivo (iOS)
xcrun simctl terminate booted com.cocos.trading
xcrun simctl launch booted com.cocos.trading
Si cambiás el candidate id, reiniciá Metro

Las variables EXPO_PUBLIC_* quedan escritas adentro del bundle cuando Metro lo arma, no se leen en vivo. Cambiar EXPO_PUBLIC_CANDIDATE_ID en el .env no tiene ningún efecto hasta que reinicies Metro limpiando caché — y la app no avisa nada, sigue operando sobre el inquilino viejo. Lo mismo vale para EXPO_PUBLIC_BUGS_TIER cuando querés activar un nivel de defectos. 

bunx expo start --clear
