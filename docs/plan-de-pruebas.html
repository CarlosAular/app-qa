  • El esfuerzo se concentra donde se pierde plata. La cadena orden → reserva → portafolio (R1, R2, R3, R6) más el doble envío (R15) y la validación del ticket (R5) son los seis riesgos Altos. 2 · Objetivo y contexto

Qué se pidió, y qué se decidió hacer con eso.

La app es un cliente de trading (React Native con Expo) que habla con una API dummy multi-tenant. El challenge no pide agregar funcionalidad: pide evaluar la calidad y automatizar la validación, y entregar cuatro cosas: un plan de pruebas, una suite automatizada con su documentación de ejecución, un reporte de bugs y un README con las decisiones. Lo que más pesa es el criterio propio: qué se prueba, qué no y por qué.

El plan persigue tres objetivos:

  • Reducir el riesgo donde el usuario pierde dinero antes de mirar cualquier otra cosa.
  • Dejar una suite reproducible y sin flakiness, aunque el servicio resuelva las órdenes límite de forma no determinística.
  • Que cada decisión de alcance sea trazable: de un riesgo a un caso, de un caso a su automatización y a su último resultado, y de ahí a un defecto.

3.2 Fuera de alcance, y por qué

Queda afuera Por qué Qué se hizo en cambio
Pruebas de seguridad y autenticación La app no tiene login: identifica al usuario con el header X-Candidate-Id, que no es un mecanismo de autenticación. Un pentest no es el objeto del challenge. Se verifica el aislamiento entre cuentas (COCOS-35), que es lo que sí puede fallar.
Rendimiento y carga El servicio es una API dummy compartida; medir tiempos o capacidad contra ella no dice nada del producto. Nada. Se anota como límite.
Accesibilidad completa Auditarla exige otro alcance y herramientas propias. Se reportó el hallazgo puntual que apareció al automatizar: el ticket era inoperable con VoiceOver en iOS (defecto #46), y se corrigió con una línea. La prueba con VoiceOver quedó documentada como COCOS-52, sin ejecutar.

Doble reserva de acciones (COCOS-45) Depende de que una orden límite siga pendiente, y el servicio la resuelve al leer la cuenta, con un factor aleatorio. Queda manual. Es candidato a un test de API sin lecturas intermedias.
Dispositivos físicos, otras versiones de sistema, tabletas Un simulador o emulador por plataforma alcanza para el alcance funcional; el resto multiplicaría el costo sin cambiar las conclusiones. Se anota como límite. Una prueba en horizontal en Android destapó el defecto #3.
Lógica interna del backend Se prueba como caja negra a través de su contrato. Suite de API con validación de esquema.

Cada cosa se prueba en el nivel más barato que la puede detectar.

Cómo leer las columnas

Manual iOS y Manual Android son las dos corridas manuales de Qase (50 casos cada una; COCOS-51 se agregó después). Un ✗ ahí es un caso que encontró un defecto, no una falla de la prueba. Appium y API muestran lo que hoy devuelven las suites. En iOS, los ocho casos originales (COCOS-5, 6, 7, 10, 25, 28, 47 y 49) dieron 4 de 8 en su corrida, y no se volvieron a correr tras los arreglos de esta ronda; se marcan con «?». COCOS-52 (VoiceOver) está documentado y todavía sin ejecutar: no figura en ninguna corrida. COCOS-42 y COCOS-53 corren en la suite de API como tests de defecto (@defecto) y fallan porque el servicio no los cumple; COCOS-24 tiene además un test de defecto propio que queda fuera de la corrida base.

Dónde la automatización cubre menos que el caso

Un ✓ en Appium significa que el test pasa, no que el caso completo pase a mano. En cuatro casos la suite verifica un tramo:

  • COCOS-43: la suite comprueba la etiqueta ACCIONES o MONEDA en los resultados de Buscar. El paso del listado de Mercados, que no muestra el tipo (defecto #20), sigue fallando a mano.
  • COCOS-30: el signo de la ganancia solo se verifica en cero, porque el servicio no mueve precios en off; el formato del rendimiento falla por el defecto #25.
  • COCOS-22 en Android: el acceso desde la ficha de la posición cae al de Mercados, porque el botón «Operar esta posición» queda tapado por la barra (defecto #2). El flujo lo deja escrito en el log y en el resultado.
  • COCOS-8, 29 y 46: el paso intermedio acepta «reservado o ya liberado», por lo dicho en 7.4; los pasos finales son exactos.

7 · Decisiones de automatización

El criterio detrás de las herramientas y de cómo se escriben los tests.

7.1 Por qué Appium

  • Es el único de los candidatos (frente a Maestro y Detox) que habla W3C WebDriver contra iOS y Android, así que un mismo test corre en las dos plataformas y el modelo de páginas es compartido de verdad.
  • Los casos exigen aritmética dentro del test: verificar que floor(monto / precio) nunca redondee hacia arriba, y comparar importes en formato es-AR por delta. Maestro es YAML declarativo y no puede parsear ese texto ni calcular el esperado.
  • Permite mezclar UI y HTTP en el mismo test, que es lo que hace viable el aislamiento por tenant: se siembra el estado por API y se verifica por UI.
  • Tiene reporter oficial de Qase, además de Allure y JUnit.

7.2 Cómo se evita la flakiness

  • Serial y sin reintentos. Los specs comparten tenant, así que paralelizar haría que los deltas de un worker midan los movimientos de otro. Reintentar un spec que ya movió plata mediría sobre una cuenta distinta a la fotografiada.
  • Aserciones por delta, nunca contra el millón inicial, y cada spec se autoabastece: la posición que necesita la siembra por API.
  • Esperas por condición: se reintenta hasta que la aserción pase, en vez de dormir a ciegas. Las pausas cortas que quedan son para que una animación termine de asentarse.
  • Binarios de release, no de debug: embeben el bundle (la suite no depende de Metro) y no tienen la capa de avisos que en debug tapa la barra de pestañas y se traga los toques.
  • Órdenes límite: invariantes, no estados (7.4).

7.3 Sin POST /reset

Requisito explícito del challenge

Documentar cómo montar la automatización en un entorno donde POST /reset no sea posible. Es la situación de esta suite: la consigna lo prohíbe.

El identificador de cuenta (EXPO_PUBLIC_CANDIDATE_ID) se inlinea al empaquetar, así que el tenant contra el que habla la app queda congelado en el binario y no puede variar por test. De ahí sale el diseño:

  1. El script de build genera un identificador por build, lo hornea, verifica con grep que haya quedado dentro del bundle y lo escribe en un archivo de información de build.
  2. El proceso de test lee ese archivo: su cliente HTTP apunta al mismo tenant que la app. Nunca se recalcula del lado del test.
  3. Las aserciones son por delta.
  4. Cada spec se autoabastece por POST /orders.
  5. Un worker y sin reintentos, por lo dicho en 7.2.

Para forzar una cuenta virgen basta recompilar: cada build nuevo es una cuenta nueva. La suite de API, que no depende de un binario, genera un identificador nuevo por test. Ninguna de las dos necesita limpiar nada, y las dos funcionan igual donde /reset no exista. El botón «Reiniciar cuenta» de la propia app se prueba por UI (COCOS-13 y 50) y ese spec corre siempre último.

7.4 Órdenes límite no determinísticas

El servicio resuelve las órdenes límite al leer la cuenta y con un factor aleatorio, así que un estado puntual no se puede afirmar. Lo que sí se mantiene, y se midió, es un invariante: una orden no ejecutable (compra por debajo del mercado, venta por encima) nunca se ejecuta (0 de 40 observadas) y termina rechazada. Los tests se apoyan en eso:

  • Los pasos intermedios afirman pertenencia a un conjunto: el efectivo o las acciones están reservados o ya liberados, y se deja constancia de cuál se vio.
  • Los pasos finales afirman el estado terminal: rechazada, nunca ejecutada, y efectivo o cantidad exactamente iguales a los iniciales.
  • Para llegar al estado final se sondea la API (unos 300 ms por lectura, hasta 40), que es lo mismo que refrescar la pantalla sin pagar unos 5 s por refresco.
  • COCOS-48 (orden del historial) no depende de esto: son doce órdenes a mercado.

7.5 Casos que fallan por un defecto de la app

Cuatro casos de UI (COCOS-15, 18, 30 y 41) y los tests de defecto de API de COCOS-42 y COCOS-53 fallan porque la app o el servicio no cumple lo que el caso afirma. El test está bien escrito: verifica el comportamiento correcto, y ese comportamiento todavía no existe. No se silencian ni se marcan como fallo esperado, porque un test en rojo que documenta un defecto es la forma más honesta de reportarlo, y se vuelve verde solo cuando el defecto se corrige. Se listan en el README para que nadie los confunda con una regresión de la suite.

7.6 Lo que enseñaron las plataformas

  • En iOS 26 la barra de pestañas se colapsa a dos círculos al scrollear, y un toque por geometría cae sobre una fila. La suite expande la barra tocando el círculo de la pestaña activa, como haría una persona.
  • El sheet del ticket era opaco para VoiceOver en iOS (defecto #46), y eso bloqueaba toda la automatización en iOS. Se resolvió con una línea en ModalContext.tsx: es la única modificación hecha al código de la app.
  • En la ficha de una posición, el scroll nativo de WebDriverAgent no converge y el gráfico absorbe los gestos del centro; se scrollea desde el margen.
  • En Android, cambiar de pestaña justo después de cerrar el ticket puede caer sobre el fondo atenuado del sheet que se cierra; la suite verifica la pestaña seleccionada y reintenta.

7.7 Reportes e integración

  • Reportes: Allure (HTML), JUnit y Qase. Cada test declara su caso con qase(id, …) y cada paso del caso es un paso del reporte. Al fallar se adjuntan una captura y el árbol de accesibilidad.
  • Qase apagado por defecto en local; se enciende con una variable y un token que va en un archivo ignorado por git.
  • CI: dos workflows. api.yml corre lint, formato, tipos, tests unitarios y la suite de API en cada push y PR, y de noche los niveles con defectos y los tests @defecto. e2e.yml corre Android en cada push y iOS de noche y a pedido. Los dos están escritos y validados en su estructura, pero todavía no corrieron en GitHub (sección 12).

Supuestos

  • Con X-Enable-Bugs: off el servicio es el golden path: cualquier fallo es real.
  • El servicio es compartido y ajeno: puede cambiar sin aviso. Por eso los tests afirman relaciones (deltas, invariantes) y no valores absolutos que dependan de él.
  • En el nivel off el servicio no mueve precios, así que el precio promedio de compra siempre coincide con el último y la ganancia real es siempre cero. El caso del signo de la ganancia (COCOS-30) se acota a verificar el formato en cero; un signo positivo o negativo real no se puede ejercitar contra este entorno.
  • Las órdenes límite se resuelven al leer la cuenta, con un factor aleatorio.
  • Se permite modificar la app si hace falta para automatizarla, documentando qué y por qué. Se modificó una línea.
  • Un identificador de cuenta por corrida; las cuentas no se limpian.

9 · Criterios de entrada, salida y aprobación

Criterio Se cumple cuando
Entrada Hay un binario compilado con el identificador verificado dentro del bundle, el dispositivo está booteado, el servicio responde en off y las dependencias están instaladas.
Un test está terminado Declara su caso de Qase, corre solo y en la suite completa, no depende del estado que dejó otro, y pasa en las dos plataformas o documenta por qué no.
Salida de una corrida Todo verde salvo los casos que fallan por un defecto conocido y documentado. Un rojo nuevo es una regresión hasta que se demuestre lo contrario.
Sin flakiness Sin reintentos, sin esperas fijas y sin depender de un estado no determinístico. Un test que pasa solo y falla en secuencia se trata como defecto de la suite y se corrige.
Calidad del repositorio Lint, formato y tipos limpios, y los tests unitarios en verde.

12 · Límites del plan y pendientes

Lo que este plan no garantiza, dicho sin maquillaje.

Casos sin automatizar Motivo Cobertura alternativa
45 Doble reserva de acciones. Exige que la primera venta límite siga pendiente cuando se envía la segunda, y la API resuelve las límite al leer la cuenta, con un factor aleatorio: cualquier lectura intermedia la deshace. Cubrible a nivel API, sin lecturas entre las dos órdenes. Queda como mejora.
16, 19, 23, 26, 31 Casos visual: superposiciones y recortes. Appium valida la jerarquía de vistas, no píxeles. Se ejecutaron a mano en las dos plataformas y destaparon los defectos #2, #3, #4, #22 y #24.
52 Prueba con VoiceOver. Appium lee el árbol de accesibilidad pero no lo escucha, y el simulador de iOS no soporta VoiceOver: hace falta un iPhone físico. Documentada en Qase y todavía sin ejecutar. El arreglo del defecto #46 solo se comprobó por el árbol de accesibilidad.
14, 33, 38 Necesitan cortar la red. En Android se haría con adb shell svc wifi disable, pero el simulador de iOS no tiene equivalente. Sin paridad entre plataformas, no entran. Se ejecutaron a mano en Android; en iOS quedaron bloqueados. Destaparon el defecto #44.
  • No se corrió la suite de UI completa de una sola vez en Android con todos los casos actuales (rondaría los 45 minutos). Cada spec se verificó por separado, y los specs de órdenes límite también en secuencia.
  • En iOS los casos nuevos se verificaron spec por spec, y los ocho originales no se re-corrieron tras los arreglos.
  • El CI nunca corrió en GitHub. Los dos workflows (api.yml y e2e.yml) están escritos, pero no se probaron hasta que el repositorio se publique. Los comandos que ejecutan sí se corrieron en local.
  • En iOS la venta límite cierra el ticket sola unos segundos después de enviarse. La orden llega igual. La suite lo tolera y lo verifica contra la API; la causa no se confirmó y por eso no está registrado como defecto.
  • Un dispositivo por plataforma: no hay evidencia sobre otros tamaños ni versiones.
  • El defecto #46 (VoiceOver) está resuelto en Qase, pero solo se verificó por el árbol de accesibilidad, no con VoiceOver activado. Esa prueba manual quedó documentada como COCOS-52 y no se ejecutó.
  • Sin Postman: lo opcional del contrato queda cubierto por la suite de Playwright con validación de esquema.

13 · Cómo ejecutar todo

bun install

# Todo en un comando: calidad, API y UI (compila los binarios que falten)
bun run qa

# Lo mismo sin dispositivos: unos 20 segundos
bun run qa:rapido

# UI · Android (compila el APK de release y hornea el identificador)
bun run e2e:build:android
bun run e2e:android

# UI · iOS
bun run e2e:build:ios
bun run e2e:ios

# Las dos plataformas, una después de la otra
bun run e2e

# Reporte HTML de Allure
bun run e2e:report

# API (línea base) y los cuatro niveles de defectos
bun run test:api
bun run test:api:tiers
bun run test:api:defectos     # los defectos conocidos: fallan porque el servicio no los cumple

# Unitarios, lint, formato y tipos
bun test
bun run lint
bun run format:check
